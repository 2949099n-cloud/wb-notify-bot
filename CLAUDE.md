# wb-notify-bot

Мультитенантный Telegram-бот с уведомлениями о заказах Wildberries (новый заказ / отмена / выкуп) через официальный API WB (dev.wildberries.ru), плюс закреплённая ежедневная сводка и меню с доп. функциями. Один бот — много независимых пользователей, каждый подключает свой магазин сам через `/addshop`.

## Правила проекта (постоянные, не забывать между сессиями)

1. **Мультитенантность обязательна.** Магазины хранятся в БД (`shops`: `owner_user_id`, `telegram_chat_id`, зашифрованный токен, `token_status`), а не в `.env`. Каждая факт-таблица несёт `shop_id`. **Изоляция по `shop_id`/`owner_user_id` без исключений** — ни один запрос не должен возвращать данные чужого магазина.
2. **`shops.id` — `INTEGER PRIMARY KEY AUTOINCREMENT`**, никогда не переиспользуется (гарантия SQLite, не ручная дисциплина).
3. **WB-токен магазина хранится только зашифрованным** (`cryptography.Fernet`, ключ — `TOKEN_ENCRYPTION_KEY` в `.env` сервера, см. `security/tokens.py`). Расшифровывается только на момент конкретного вызова WB API (`shops_repo.get_decrypted_token`), не хранится в памяти дольше необходимого и никогда не логируется в открытом виде.
4. **Онбординг — `shops_repo.register_shop()`, общая функция для CLI и `/addshop`.** При добавлении магазина: живая проверка токена (`ping`), попытка авто-определить имя через `seller-info`, шифрование, запись. При `/addshop` в Telegram — **сообщение с сырым токеном удалять из чата сразу после обработки**.
5. **401 от WB — статус, не падение.** Помечать магазин `token_status='invalid'` (`shops_repo.mark_token_invalid`), писать алерт в `shop_alerts`, не ронять опрос остальных магазинов. Опрос всех активных магазинов — `asyncio.gather(..., return_exceptions=True)`.
6. **Лимит склада «1 запрос/мин» — per-token (per-магазин), не глобальный.** Не нужно разносить запросы МЕЖДУ разными магазинами, только повторные вызовы одного и того же (и так решается интервалом опроса 30 мин).
7. **Перед реализацией/правкой любого модуля в `wb_api/*`** — сначала WebSearch актуальной документации на dev.wildberries.ru (эндпоинты, поля, лимиты периодически меняются, не полагаться только на память).
8. **Тексты уведомлений (RU + эмодзи) в `telegram/formatters.py` менять нельзя** без явного запроса пользователя — формат утверждён и должен совпадать с референсным ботом FenixWB дословно.
9. **"Остатки подробно"** считается для трёх окон сразу — 7/30/60 дней (не одно дефолтное), по каждому складу отдельно (не агрегируя, в отличие от блока аналитики в обычном уведомлении).
10. **Денежная/расчётная логика (`calc/metrics.py`) обязательно с unit-тестами** — деление на 0 → `"∞"`, а не ошибка.
11. **WB API не поддерживает вебхуки** — только поллинг (15–30 мин), архитектура на этом не должна меняться.
12. Разработка — по шагам из плана ниже, с проверкой каждого шага, не писать всё сразу.

## Стек

Python 3.11+, `httpx.AsyncClient` (WB-клиент асинхронный — нужен для `asyncio.gather` по магазинам), `python-telegram-bot`, SQLite (`src/wbnotify/db.py`, доступ синхронный через `sqlite3`), `cryptography.Fernet`, `APScheduler`, `pytest`.

## Структура

```
src/wbnotify/
  config.py             # .env -> Config (Telegram-токен, ключ шифрования, интервалы; БЕЗ магазинов)
  db.py                  # схема SQLite (shops с owner_user_id, shop_alerts, ...)
  models.py              # ShopRow и т.д. — БЕЗ сырого токена в датаклассе
  security/tokens.py     # encrypt_token/decrypt_token (Fernet)
  shops_repo.py           # register_shop/list_active_shops/get_decrypted_token/mark_token_invalid —
                           # единая точка входа для CLI (шаг 2) и /addshop (шаг 4)
  wb_api/                 # асинхронные клиенты WB API (client.py: WBAuthError на 401, retry/backoff на 429/5xx)
  sync/                   # инкрементальный забор данных в БД, по магазину, вызывается через asyncio.gather
  events/classify.py      # детект Заказ/Отмена/Выкуп/Возврат, дедуп, notification_queue
  calc/metrics.py         # расчёты: % выкупа, скорость заказов, дней остатка
  telegram/                # formatters (шаблоны), sender, bot (/addshop и др.), keyboards, daily_summary
  scheduler/               # jobs, runner (точка входа процесса)
scripts/
  check_connectivity.py   # смоук-тест Telegram + ключа шифрования (шаг 1; WB-токены больше не здесь)
  sync_cli.py              # register (= /addshop без Telegram) + sync (шаг 2)
```

Прошлое открепляется — в шапке чата ровно одна, свежая сводка. Нет прав закреплять (группа) или недоступен чат одного участника — сводка всё равно уходит остальным, оба случая покрыты тестами.
  - Состав: заказы / продажи / отмены / возвраты за день с суммами, средний чек, топ-5 товаров по заказам, до 5 товаров, которые заканчиваются. Источники те же, что в блоке аналитики уведомлений, чтобы цифры не расходились: заказы — из воронки продаж, выкупы и возвраты — из `sales`. **Отмены — по `orders.cancel_date`**, а НЕ по возвратам: в уведомлении «Отмена заказа» строка «Вчера/Сегодня» намеренно считается по возвратам (решение пользователя), но для итога дня нужны именно отменённые заказы.
  - Остаток в блоке «заканчивается» считается ПО АРТИКУЛУ (как скорость заказов), а нулевой пишется словом «закончился» — «≈ на 0 дн.» читалось как «скоро кончится», хотя товара уже нет.
  - Суммы — целыми рублями с пробелом между тысячами (`_rub`). В самих уведомлениях формат прежний (`_fmt_money`), менять его нельзя (правило 8).

## Проверенные вживую факты о WB API (важно, расходятся с исходным ТЗ — не доверять памяти/ТЗ, доверять этому списку)

- `/api/v1/supplier/orders` и `/api/v1/supplier/sales` (statistics-api.wildberries.ru) — **НЕ возвращают `chrtId`**, только `nmId`+`techSize`+`barcode`. Лимит: orders 1 запрос/мин (всплеск 10), sales 1 запрос/мин (без всплеска, легко словить 429 при ручном тестировании).
- Остатки по складам — старый `/api/v1/supplier/stocks` отключается WB. Актуальный эндпоинт: `POST https://seller-analytics-api.wildberries.ru/api/analytics/v1/stocks-report/wb-warehouses`, body `{nmIds, chrtIds, limit, offset}`, ответ `data.items[]` с полями `nmId, chrtId, warehouseId, warehouseName, regionName, quantity, inWayToClient, inWayFromClient` — **НЕТ techSize/barcode**. Токен категории "Аналитика". Лимит 3 запроса/20с, всплеск 1.
- Связка chrtId↔techSize↔barcode — только через `POST /content/v2/get/cards/list` (content-api.wildberries.ru), поле `sizes[]` каждой карточки: `{chrtID, techSize, wbSize, skus[]}`. Оттуда же `dimensions.{length,width,height,weightBrutto}` для габаритов.
- **Rate-limit retry — заголовок `x-ratelimit-retry` (секунды), НЕ стандартный `Retry-After`.** Без этого backoff в `wb_api/client.py` не успевал выждать реальное окно лимита (поймано вживую на 429 от `/sales`). Уже исправлено и проверено.
- Токен `seller-info` (common-api.wildberries.ru/api/v1/seller-info) даёт `name`/`tradeMark`/`sid` — используется для авто-имени магазина при `/addshop`.
- Комиссия: `GET /api/v1/tariffs/commission` (common-api), `?locale=ru`, ответ `report[]` с `subjectName` (совпадает 1:1 с `orders.subject`) и полями `kgvpSupplier`/`kgvpMarketplace`/`kgvpPickup`/`kgvpBooking`/`kgvpSupplierExpress`/`paidStorageKgvp`. Лимит 1 запрос/мин (всплеск 2).
- Логистика: `GET /api/v1/tariffs/box` (common-api), `?date=ГГГГ-ММ-ДД` (обязателен), ответ `response.data.warehouseList[]` со СТРОКОВЫМИ числами через запятую (`"78,2"`) и `"-"` как "не применимо". `boxDelivery{Base,Liter,CoefExpr}` — для FBW, `boxDeliveryMarketplace{...}` — для FBS. **warehouseName в этом списке — крупные логистические хабы (страны/города), НЕ конкретные фулфилмент-центры из `/orders`** — прямое совпадение по имени редкость/не гарантировано.
- `/api/tariffs/v1/acceptance/coefficients` (с полями конкретных складов типа "Сц Брянск 2") — **временно отключён самим WB**, не наша проблема.
- Рейтинг/отзывы: `POST /api/analytics/v2/item-rating` (seller-analytics-api), body обязательно требует `currentPeriod`+`orderBy`+`offset`, до 50 `nmIds` за раз. **`currentPeriod.end` не может быть сегодняшней датой** (400 "current period end date cannot be today") — использовать вчера. `data.items[].feedbackRating.current` — рейтинг, НЕ зависит от периода. `data.items[].feedbackCount.current` — ЗАВИСИТ от периода (не лайфтайм-счётчик отзывов) — максимум 365 дней в одном запросе.
